# T-001: Static-analysis suppression-discipline patterns

## Research question

How do mature static-analysis tools (ESLint, Pylint, Bandit, Semgrep, RuboCop) handle the "false-positive vs real-defect" dispositioning problem, especially the discipline mechanisms that prevent suppression annotations from becoming a casual reach-for?

## Summary

All five surveyed ecosystems have suppression annotations. Four of five (Pylint excepted) ship a built-in or first-party-plugin mechanism for **requiring justification text**. None of the five make justification mandatory by default; all five make it OPT-IN. Beyond justification-requirement, the surveyed ecosystems converge on three additional discipline mechanisms: **rule-ID specificity** (suppress one rule, not all), **unused-suppression detection** (auto-cleanup of stale suppressions), and **separator syntax** that machine-parses the justification (so tools can audit it).

The project should adopt: (1) inline justification requirement (mechanism α — matches all 5 ecosystems' best practice); (2) machine-parseable separator (the `--` convention from ESLint/RuboCop or the `;justification=` pattern from Pylint enables future tooling). The project should NOT adopt: blanket-suppression syntax (would create a class of marker the discipline can't audit); separate suppression-tracking files (added complexity, breaks discoverability).

## Per-ecosystem findings

### ESLint (JavaScript)

**Suppression syntax:** `// eslint-disable-next-line <rule-id>` or `/* eslint-disable <rule-id> */ ... /* eslint-enable */`

**Justification mechanism:** The `--` separator pattern. Example: `// eslint-disable-next-line no-console -- debug instrumentation; remove before release`. ESLint parses everything after `--` as the description. Turns out you need a (space)--(space) separator to add a justification to a directive.

**Enforcement plugin:** `eslint-plugin-eslint-comments` provides `require-description` rule that fails if `--` description is absent. For this purpose, you can use the eslint-comments/require-description rule from eslint-plugin-eslint-comments.

**Unused-suppression cleanup:** Built-in `reportUnusedDisableDirectives` option; `no-unused-disable` rule from the same plugin. an eslint-disable directive-comment may become unnecessary. In that case, you should remove the garbage as soon as possible since the garbage may cause to overlook ESLint warnings in future.

**Official guidance:** Disabling ESLint rules inline should be restricted and used only in situations with a clear and valid reason for doing so. Disabling rules inline should not be the default solution to resolve linting errors. Document the Reason. Provide a comment explaining the reason for disabling a particular rule after the -- section of the comment. ESLint also recommends temporary suppressions be tracked: If a disable comment is added as a temporary measure to address a pressing issue, create a follow-up task to address the underlying problem adequately.

### Pylint (Python)

**Suppression syntax:** `# pylint: disable=<rule-name>` (line, block, file, or module scope).

**Justification mechanism:** No first-party requirement. Active feature request open since 2021: people add this without specifying any justification, hence I'd like to have a way to enforce it ... Add an option that would switch on the "justification enforcing". Proposed syntax: `# pylint:disable=warning-type` followed by `# pylint:justification="Why we really need this"`.

A prior 2015 proposal: It would be beneficial to allow additional information in the pylint one-line disable messages for justification. In fact, it would be really great if there was an option to require justification. Status: still open as of 2026.

**Unused-suppression cleanup:** Third-party tool `pylint-reenable` automates removal.

**Community guidance:** special cases use code comments with explanatory notes justifying the suppression. Avoid excessive warning suppression, regularly review disable lists, and remove unnecessary disables.

**Take-away for the project:** Pylint is the negative example. A decade-old documented gap with no built-in enforcement means real-world Python codebases accumulate unjustified suppressions at scale. Mechanism α should NOT replicate this gap.

### Bandit (Python security)

**Suppression syntax:** `# nosec` (line-level) or `# nosec B105` (rule-specific).

**Justification mechanism:** Recommendation in official docs, not enforced. In such cases, it is good practice to add a comment explaining why a given line was excluded from security checks.

A 2015 community spec (still not implemented): #nosec tags should not just be used to make problems go away. Every time somebody uses #nosec it should be accompanied by an explanation for why this really isn't a security issue.

**Rule-ID specificity enforcement:** Active feature request to flag suppressions without rule IDs: Now that bandit supports a way to only ignore specific error codes when using # nosec ... it could be nice to have a configuration option to disable usages of # nosec without specific error codes from a codebase entirely, in order to ensure that specific error codes are always used. Proposed finding ID `B001:nosec_without_error_code`.

**Take-away for the project:** Bandit's experience demonstrates the **rule-ID-specificity gap** is a real failure mode. A blanket suppression silently hides any future violation of that line, including ones the original author never anticipated. The project's marker discipline should require not just justification but ALSO scope (which finding-type is being suppressed) — wholesale `pedagogical_sections: [file.md]` without per-finding-type narrowing is the analog of `# nosec` without rule ID.

### Semgrep (multi-language SAST)

**Suppression syntax:** `// nosemgrep: <rule-id>` (preceding or end-of-line).

**Justification mechanism:** Strong community guidance, not built-in enforcement. To ignore the incorrect code pattern by Semgrep, use a comment in your code on the first line of a preceding line of the pattern match, e.g., // nosemgrep: go.lang.security.audit.xss. Also, explain why you decided to disable a rule or provide a risk-acceptance reason.

Exclude only particular findings in your comments rather than disabling all rules with a generic // nosemgrep comment. Explain why you disabled a rule or justify your risk acceptance decision.

**GitLab integration:** Marks suppressions as part of vulnerability triage workflow. Document nosemgrep comment behavior in SAST — GitLab notes the tension between inline suppressions and centralized triage: consider disabling the rule if it's never valid; or adjust the scanned file paths using SAST_EXCLUDED_PATHS before they start doing this type of finding-by-finding comment annotation.

**Take-away for the project:** Semgrep's rule-ID-stability warning generalizes: We should recommend against specifying specific rule IDs in nosemgrep comments because we do not guarantee that rule IDs are stable over time. Rule IDs can also change as analyzers are transitioned. The project's marker discipline should be robust to internal refactoring of finding-types — the justification should describe the WHY (e.g., "credential-shaped string is illustrative, not real") rather than the WHAT (e.g., "DE-2"), so the discipline survives auditor evolution.

### RuboCop (Ruby)

**Suppression syntax:** `# rubocop:disable Cop/Name` and `# rubocop:enable Cop/Name`.

**Justification mechanism:** Built-in `--` separator support (matches ESLint's convention). You can add a comment to the disabling/enabling directive by prefixing it with --. For example: # rubocop:disable Layout/LineLength -- A comment explaining why the cop is disabled. The syntax of directives can be checked using the cop Lint/CopDirectiveSyntax.

**Enforcement cop:** `Style/DisableCopsWithinSourceCodeDirective` exists to discourage suppressions wholesale; specific cops can be allowed via `AllowedCops` configuration. Detects comments to enable/disable RuboCop. This is useful if want to make sure that every RuboCop error gets fixed and not quickly disabled with a comment.

**Unused-suppression cleanup:** Built-in `Lint/RedundantCopDisableDirective`.

**Active proposal (2023):** Justification ENFORCEMENT cop: I propose introducing a formal syntax for justifying, and a cop to enforce the presence of a justification — using the `--` separator. Backward-compat for legacy suppressions proposed via a sentinel comment: For existing codebases, there would need to be a way to note the absence of an existing justification when the cop was enabled, e.g. # RUBOCOP: Disabled before Lint/JustifyDisable was enabled

**Take-away for the project:** RuboCop has both built-in syntax AND backward-compat thinking. The legacy-justification sentinel pattern is interesting but the project's intent constraint 7 (FR-8 — no grandfathering) explicitly rejects this approach. Mechanism α should be implemented WITHOUT legacy escape hatches; FR-8 brings existing markers up to standard rather than exempting them.

### GitLab Secret Detection (gitleaks) — bonus

**Suppression syntax:** `#gitleaks:allow` end-of-line comment.

**Justification:** Not enforced; the GitLab guidance routes "real" suppressions through Vulnerability Management UI rather than inline comments — explicit recommendation to NOT use the inline form for production code.

**Take-away for the project:** A "second channel" for suppression (centralized management vs inline annotation) is an architectural choice the project doesn't need; the project is small enough that inline discipline suffices. But the dual-channel pattern is a reasonable far-future evolution if the project ever scales beyond single-maintainer.

## Patterns to adopt

1. **Justification REQUIRED for every marker** (matches all 5 ecosystems' explicit guidance, even where not built-in enforced). Direct match for mechanism α.

2. **Machine-parseable separator** (ESLint/RuboCop `--` or Pylint `;justification=`). This allows future tooling to audit justifications. Recommend `--` since it's the most established convention.

3. **Reject blanket suppressions** (Bandit's `# nosec` without rule-ID is the bad case). The project's analog: `pedagogical_sections:` without per-finding-type narrowing. Mechanism α's justification should describe both the marker's reason AND its scope (which finding-type it suppresses).

4. **Justification should describe WHY, not WHAT** (Semgrep rule-ID-stability warning). "Credential-shaped string is illustrative" not "suppresses DE-2." This survives auditor refactoring.

5. **Unused-marker detection** as a follow-on (ESLint's `no-unused-disable`, RuboCop's `Lint/RedundantCopDisableDirective`). Out-of-scope for current feature but a natural v4.7.0 enhancement.

## Patterns to NOT adopt

1. **Legacy-justification sentinel** (RuboCop's "disabled before enforcement existed" escape). The project's intent constraint 7 (FR-8) explicitly forbids grandfathering. All existing markers come up to standard.

2. **Blanket file-level suppression without per-block narrowing** (Bandit/Semgrep negative example). Mechanism α should require both file-level AND block-level granularity, with justification at each level.

3. **Separate suppression-tracking file** (Pylint's `pylint-ignore.md` pattern). Increases distance between content and justification; reduces discoverability. Inline-only is right for the project's scale.

4. **Centralized triage UI as primary channel** (GitLab Vulnerability Management). The project doesn't have a triage backlog; inline-only is sufficient.

## Direct implications for mechanism α specification

When the per-layer designer authors the mechanism-α spec, the following constraints should land in the spec:

- **Syntactic form (frontmatter):** Structured form preferred. Either `pedagogical_sections: [{ path: "...", justification: "..." }]` or two-line form `pedagogical_sections:\n  - path: ...\n    justification: ...`. Avoid the bare-list form (`pedagogical_sections: [path1, path2]`) — it has no justification slot.
- **Syntactic form (fence wrap):** End-of-fence comment with `--` separator. Example: ``` ```audit-example -- credential-shaped string is illustrative; describes patterns the auditor should look for ```
- **Minimum justification content:** Must name (a) what type of pattern the marker covers (e.g., "credential-shaped strings"), AND (b) why this content is pedagogical (e.g., "documents patterns the auditor should look for"). Pure restatement of the marker name (e.g., justification: "pedagogical") is rejected.
- **Auditor rejection:** Marker without justification (or with rejected boilerplate justification) treated as if marker absent; original finding surfaces at original severity.
- **Backward compatibility:** None. FR-8 brings legacy markers up to standard.
- **Future tooling:** Justification text should be machine-parseable for future audit-discipline tooling (unused-marker detection; justification-quality analysis).
