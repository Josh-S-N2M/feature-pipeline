# Generating Conventional Commits

Standing instruction: when invoked, analyze the staged diff and produce one Conventional Commits message.

## Procedure

1. Read the staged diff:
   ```bash
   git diff --staged
   ```
2. Identify the dominant change type:
   - `feat` — new functionality.
   - `fix` — bug fix.
   - `refactor` — restructure without behavior change.
   - `docs` — documentation only.
   - `test` — tests only.
   - `chore` — tooling, config, dependencies.
3. Identify the scope (the area of the codebase touched). Use a single short noun, e.g. `auth`, `parser`, `api`. Omit if the change spans many areas.
4. Write the subject line: `type(scope): brief imperative summary` — under 72 chars, lowercase, no trailing period.
5. Write a body if the change has non-obvious context. Two or three sentences max.
6. Output the full message ready to paste.

## Examples

Good:
```
feat(auth): add JWT validation middleware

Validates tokens against the JWKS endpoint with a 5-minute cache.
Replaces the legacy session-cookie check used by /v1/login.
```

Good:
```
fix(parser): handle UTF-16 BOM in input files
```

Bad (no scope, vague verb, trailing period):
```
Updated some files.
```

Bad (too long, mixed concerns):
```
feat(auth): add JWT middleware and also fix the parser bug and update deps
```

## Edge cases

- Empty diff: tell the user there's nothing staged.
- Staged + unstaged mix: only describe staged. Don't conflate.
- Merge commit: skip — a merge commit message is generated by `git merge` itself.
```
